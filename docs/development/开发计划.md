**可能的问题说明**

分镜完全由随机数序列决定，所以**任何改变掷骰次数或顺序的改动都会让整片换一套镜头**，
观感上等于"完全不同的作品"，而每个部件自身的绘制仍然是正确的。排查时先判断随机流有没有错位，
再看部件本身；下面每一行都是一次错位的具体成因。

| 触发点               | 机制与判断依据                                                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 首镜是否掷特效骰     | 无标题卡时第一镜多掷一次 `chance()`，本行后续镜头全换，并经 `history` 的去重降权传给之后每一行。守卫条件是「首镜不掷」，改 `pickFx` 时必须保留                                                                     |
| 开关判断与掷骰的顺序 | 必须**先判 `fxOn(...)` 再 `rng.chance(...)`**。反过来会让「关掉某个特效开关」这个动作本身消耗随机数：面板开关失效，分镜也随之跑偏                                                                                  |
| 分部注册顺序         | `rng.wpick` 逐项累减权重，同一批件换个顺序就抽出别的件。核心装饰顺序以 `engine/packs/decor.ts` 声明的 `DECOR_ORDER` 为准，`registry.ts` 不得按对象字面量的书写顺序推导；未列出的键追加在后，避免将来漏配时静默丢件 |
| 风格权重的语义       | 风格包里的 `decor` 权重是**存在即替换**默认值，不是乘以默认值；写成乘法则该件相对权重整体偏掉                                                                                                                      |
| 密度常量的命名方向   | 每镜目标时长 `L` 越小镜头越多。常量按 `sparse` / `dense` 命名而非 `min` / `max`，就是为了防止 `lerp` 两个参数接反——反了会数值不等且方向相反                                                                        |
| 去重历史的写入范围   | 只有边缘特效进 `fxHistory`；中途特效只 `addEvent` 不 push，否则后续「近 3 次用过就 ×0.2 降权」的依据变了，特效分布偏移                                                                                             |
| 手推公式             | 后期特效的条带数与条带高度一律走 `util.ts` 的 `hash()` / `rr()`。手推线性映射容易算错，漏掉哈希会让条带数变成随 24Hz 时钟线性循环                                                                                  |
