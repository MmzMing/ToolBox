## 1. 结论摘要

用户反馈"很多镜头和构图里面的画面完全对不上旧项目，绝大部分都对不上"。

排查结论：**画面部件本身是准的，问题全在"每个镜头挑哪一件部件"的规划器上。**

- 部件库忠实：构图 141 件、镜头运动 28 件、背景图形、装饰 115 件、入场/保持/退场/文字加工，以及逐字绘制主链路 `drawItem`，在同一颗随机数下**逐条绘制指令完全一致**。
- 规划器有 6 处偏差，会让同样的输入抽出另一套部件。最致命的是：默认工程没有标题卡，于是第一镜就多掷一次随机数，**随机流从第 2 个镜头起整体错位**，之后每一镜的构图/镜头/装饰全变了——观感上就是"完全不同的作品"。

修复前（12 镜中命中的件数）：构图 3～11、镜头运动 2～12、入场 3～9、退场 2～7、保持 2～9、装饰 0～3。
修复后：**8 个种子全部 18/18 逐镜命中**（见 §5）。

## 2. 审查方法

沿用并扩展 `geometry-trace.test.ts` 已有的"录账画布"思路做**差分对账**，而不是人工读码：

1. 用 `node:vm` 把旧项目 `src/*.js` 整套跑在沙箱里（`document.createElement('canvas')` 换成只记账的桩），拿到全局 `J`；
2. 新引擎跑同一份输入，两侧的内部离屏画布也接到同一台录账画布上；
3. **共用旧引擎那颗 rng**（`rng`/`hash` 本身有单测保证两侧一致），于是差异只可能来自逻辑，不来自抽样顺序；
4. 只比对**指令名 + 数值参数**，不比对文字内容与颜色——中日文适配不会造成误报，真正的几何/流程偏差会暴露。

| 对账对象                                                                   | 结果                                                  |
| -------------------------------------------------------------------------- | ----------------------------------------------------- |
| `layout` 构图 141 件 × 3 时刻                                              | **141/141 一致**（既有 `geometry-trace.test.ts`）     |
| `cam` 镜头运动 28 件 × 5 时刻（`get()` 逐字段）                            | **28/28 一致**                                        |
| `bg` 背景图形 × 5 时刻（绘制指令序列）                                     | 可比对的 **52/52 一致**，9 件因沙箱缺 `Path2D` 未比对 |
| `decor` 装饰 115 件 × 2 时刻                                               | **113/115 一致**（1 件刻意适配，1 件待复核）          |
| `enter`/`hold`/`exit`/`treat` + `drawItem`（走 `mainDraw` 全链路）× 8 时刻 | **全部一致**                                          |
| 十组分部的 order 数组逐位对比                                              | **仅 `decor` 错位 15 件** → 缺陷 P0-3                 |
| 后期 `fx`/`trans`、HUD                                                     | 未做指令级对账（仅人工读码，见 §7）                   |

一次性对账脚本已删除；建议按 §7 固化为回归测试。

## 4. 缺陷清单与修复

严重度：P0 = 画面整体对不上；P1 = 功能失效或局部错误；P2 = 细节偏差。

### ✅ P0-1　`pickFx` 丢了"首镜不掷骰"守卫 → 随机流整体错位

- `engine/planner.ts` ／ 旧 `src/08_planner.js:302`　`if (plan.cuts.length > 1 || k > 0 || li > 0)`
- 后果：无标题卡时第一镜多掷一次 `chance()`，本行后续镜头全换一套；`history` 的去重降权再把偏差传给后续每一行。
- **修复**：补回守卫，作用于新的 `out.cuts`。

### ✅ P0-2　镜头密度 `lerp` 参数顺序接反

- `engine/planner.ts:55 / :756` 原 `lerp(CUT_LENGTH.max, CUT_LENGTH.min, d)`，旧 `J.lerp(1.3, 0.5, d)`
- 旧 = `1.3-0.8d`，新 = `0.5+0.8d`：数值不等且方向相反。诱因是常量名与实际取值相反（`min: 1.3`、`max: 0.5`）。
- **修复**：常量改名为 `CUT_LENGTH = { sparse: 1.3, dense: 0.5 }` 并按 `lerp(sparse, dense, density)` 调用，语义自解释以免再次写反。

### ✅ P0-3　`decor` 注册顺序与旧项目不一致（修复阶段新发现）

- `engine/registry.ts:104` 用 `orderOfKeys(DECOR)`（即对象字面量的书写顺序）推导随机序列，而 `engine/decor.ts:594` 早已导出一份**顺序正确**的 `DECOR_ORDER`，两者互相矛盾（`ae-export.ts` 用的是后者）。
- 15 件核心装饰错位：旧序 `brackets, rings, dots, arrows, slash, sparks, leaders, waveform, barcode, grid, stripes, blobs, bars, shapes, counter`，新序把后 6 件提到了最前。
- 为什么顺序要紧：`rng.wpick` 是逐项累减权重，同一批件换个顺序就会抽出别的件。`w` 值与 `layer/subtle` 全部一致，顺序是唯一变量。
- **修复**：`registry.ts` 合并核心装饰时按 `decor.ts` 声明的 `DECOR_ORDER` 排（并保留未列出的键追加在后，避免将来漏配时静默丢件）。
- **同时补测试**：`registry-parity.test.ts` 原来只比 key 集合，所以这个 bug 能一路绿灯过 CI；已追加"十组分部的 order 数组逐位一致"断言。

### ✅ P1-4　`pickDecor` 把风格权重从"覆盖默认值"写成"乘以默认值"

- `engine/planner.ts:417-421` 原 `(st.decor?.[k] ?? 1) * base`，旧 `wkey(st.decor, k, base)` 语义是**存在即替换**
- 风格包只要写过 `decor` 权重（`noir` 就有 `rings: 0.8`、`slash: 0.6`），该件的相对权重就被整体乘偏。
- **修复**：改为 `st.decor?.[k] ?? base`。

### ✅ P1-5　内置后期特效开关全部失效（`fxOn` 判断被删）

- `engine/planner.ts:900-918` ／ 旧 `src/08_planner.js:290-300` 每条形如 `if (fxOn('slice') && rng.chance(…))`
- 双重后果：① 面板里关掉切片/色块/反相/闪白/变焦/马赛克/抖动/色散完全无效；② 旧侧靠短路跳过 `chance()`，用户一关开关新侧就多掷一次，分镜再度跑偏。
- **修复**：恢复 9 处 `fxOn(...)` 前置判断，并保持"先判开关、后掷骰"的求值顺序。

### ✅ P1-6　中途特效被误写进去重历史

- `engine/planner.ts` 原 `fxHistory.push(mid)`，旧 `src/08_planner.js:306` 只 `addEvent` 不 push
- 后果：后续边缘特效的"近 3 次用过就 ×0.2 降权"依据变了，特效分布偏移。
- **修复**：删除该行。

### ✅ P2-7　后期"切片"两处公式改写错（修复阶段补全）

- `engine/renderer.ts` 的 slice 分支有两处，旧 `src/09_render.js:297-300`：
  1. 条带数 `6 + (clock24 % 7)` ← 应为 `6 + (J.h(st2, 3) % 7)`，哈希被漏掉，条带数变成随 24Hz 时钟线性循环；
  2. 条带高度 `clamp(-0.06 + 0.12·r + 0.06, 0.01, 0.12)` ← 手推线性映射时算错，应为 `J.rr(0.01, 0.12, …)` = `0.01 + 0.11·r`。
- **修复**：两处都改回调用 `util.ts` 已有的 `hash()` / `rr()`，不再手推公式（同段另一处 `rr(0, 0.08, …)` 顺带统一）。

### ⏸ P2-8　`decor.dimension`（寸法线）坐标不一致 —— 未处理，需浏览器复核

- 新 `engine/packs/decor.ts:1281` 起 ／ 旧 `src/11p_decor.js:438` 起
- 差异：第 23 条指令 `moveTo(944.00, 300.00)` → `moveTo(970.67, 300.00)`；两侧源码正文目视一致。
- 判断：疑似量字宽度（`textW` 走 `measureText`）路径差异，被对账桩的假字体度量放大。**只有 1/115 件受影响，且不在只有桩的情况下盲改**，留待浏览器截图比对。

### ✗ P1-6（原报告编号）→ 撤销：`useAudioLength` 不是缺陷

原报告把"新代码丢了 `T.useAudioLength !== false` 判断"列为缺陷，复查后撤回：该字段在旧项目**全部代码里只出现过那一次**（`08_planner.js:159`），没有任何地方写过它，也没有 UI 开关。取值为 `undefined` 时 `!== false` 恒真，两侧行为完全一致。属旧项目遗留的死配置，不需要移植。
